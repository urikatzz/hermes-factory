# Factory worker contract

## Managed workflow stages
When the card has a WORKFLOW header, its captured KIND and profile assignment govern this stage. KIND prepare is read-only planning even for Developer or Fixer: produce PLAN.md, numbered acceptance criteria and a Manifest include list as retained artifacts. Never repair code during preparation. Include workflow_contract="factory-workflow/v1" and the exact stage_key in completion metadata alongside factory-worker/v2. Verifier additionally records release_audit as PASS or FAIL, snapshot and publish_commands; environment_gaps maps an AC to unity_editor only when that is the sole missing environment. For managed failed_checks use {"cmd":"...","preexisting":true/false} for each failed check; plain legacy command strings remain valid. Finding scope is qualified as profile:F<n>; preserve those qualified IDs in repair findings_fixed/rejected_findings. Retain PLAN.md as an attachment but list .factory/PLAN.md and .factory/include.txt in the implementation manifest. Snapshot paths in handoffs are resolved to retained src-<manifest>.tgz attachments by the controller; explicitly set snapshot_attached:false for an oversized archive and record the limitation in report.md. Root success and repair cycles are controlled by the deterministic controller. Do not create extra stages or change the graph.

## Orientation
- You run headless (`chat -q`): nobody can answer questions. Never call clarify. `kanban_block` parks your card for a human, who sees it only on the board; use it only where this contract or your SOUL says so. For every other stop, complete with a verdict so the gate sees it.
- Start with `kanban_show()` (no args). The body header gives ROOT, STAGE, CYCLE, PROJECT_MODE, PROJECT_DIR, SLUG, MANIFEST, BASELINE, BASELINE_TGZ, INPUTS, ACCEPTANCE, SCOPE, DECISIONS. Parent handoffs are in `worker_context`; metadata there is cut at 4096 chars, so if a parent's metadata looks truncated call `kanban_show(task_id=<that parent>)` and read its latest completed run.
- Never `kanban_show` the root or sibling cards; read only your parents and cards named in INPUTS/SCOPE. The root is linked as your child: do not open it, just `kanban_complete`. Never create cards (put follow-ups in `metadata.followups`). Never shell out to `hermes`.
- Upstream stop: if a parent handoff says `VERDICT=BLOCKED`, do no work. Writers complete `VERDICT=BLOCKED` with `blocked_reason: "upstream <stage> BLOCKED: <its reason>"`; readers complete at once (verifier `FAIL`, reviewers `CHANGES_REQUIRED`) with finding `F0|BLOCKER|-|-|upstream <stage> BLOCKED` and no snapshot.
- Gate: every job has one deterministic gate command (format, lint, typecheck, tests, build); read `GATES.md` in this skill's folder before planning, implementing or verifying.
- `fw.py` below (and in your SOUL) means `python3 ${HERMES_SKILL_DIR}/scripts/fw.py` (standard library, never runs git, prints one JSON object; exit 2 = bad argument, 3 = excluded/unsafe/missing include path, 4 = manifest check failed, 5 = sha12 mismatch). Run it as its own terminal command, never through `bash -c` or a pipe.

## Manifest and workspaces
- The deliverable is exactly the files in `PROJECT_DIR/.factory/SHA256SUMS`, built only from the explicit include list `PROJECT_DIR/.factory/include.txt` (one relative file or directory per line). `.factory/PLAN.md` and `.factory/include.txt` are always included; no other `.factory/` file ever is. MANIFEST/sha12 = first 12 hex chars of sha256 of SHA256SUMS.
- Never in a manifest and never copied by anyone (case-insensitive, any path component): `.env*`, `*.env`, `n8n/`, `node_modules/`, `dist/`, `.git/`, `.worktrees/`, `screenshots/`, `.ssh/`, `.aws/`, keys/certs/keystores, credential files, `.npmrc`/`.netrc`, archives (`*.tgz`, `*.zip`), logs, `.DS_Store`, `._*`, and anything reached through a symlink. fw.py enforces this; never edit SHA256SUMS by hand. Never open, print or copy `.env*`, key files or `n8n/` contents, and never touch the user's unrelated folders in PROJECT_DIR (for example a live `n8n/` Docker stack).
- Writers (IMPLEMENT, FIX, FIX PROBE; your workspace IS PROJECT_DIR): edit only inside PROJECT_DIR (a hook blocks write_file/patch elsewhere and into `n8n/`, `.git/`, `.env*`). Temporary scripts go in `PROJECT_DIR/.factory/tmp/`. In ISOLATION: dir jobs, delete them before you complete with plain `rm <file>` and `rmdir`, at most 2 files per command and never several `rm` commands in a row (recursive `rm -r`/`rm -rf` is denied in headless runs, and the security scan hard-blocks bursts of 3+ deletions within about 20 seconds; readers use `fw.py clean` instead). In ISOLATION: worktree jobs (header) leave `.factory/` exactly as it is: it is never in the manifest, never committed and never published, so do not delete anything in it. If any delete is blocked by the security scan, leave the file, note it in `residual_risk` and carry on; never work around the block (no base64 dumps, local web servers or URL attaches). Keep include.txt complete, then run `fw.py manifest PROJECT_DIR`; review `unlisted_not_in_manifest` and add anything that belongs to the deliverable. Never write source archives into PROJECT_DIR.
- Environment: your task id is the `id` from `kanban_show()`; `$HERMES_KANBAN_TASK` is hidden from the terminal tool by design and prints empty, so never use it in commands. `$HERMES_KANBAN_WORKSPACE` is set (for writers it equals PROJECT_DIR). A missing or empty environment variable is never a reason for `VERDICT=BLOCKED`: take the value from your card (`kanban_show`) and continue. A new PROJECT_DIR is expected to be empty (no `.factory/` yet); create what the stage needs.
- Card body wins: if your card body and PLAN.md (or another input) disagree on a literal value (a marker, file name, string), follow the card body, record the mismatch in metadata `discrepancies`, and finish normally. Such a mismatch is never a reason for `VERDICT=BLOCKED`.
- Writer retries: before your first edit, write `PROJECT_DIR/.factory/started-<your task id>`. If that file already exists when you start, the dispatcher is re-running your card after a timeout or crash: skip your SOUL's start-of-stage precondition check, continue from the current tree, and finish normally.
- Readers (PLAN, VERIFY, REVERIFY, reviews; scratch workspace): never write into PROJECT_DIR, not even via terminal (no installs, builds, servers or screenshots there). PLAN reads PROJECT_DIR read-only. Everyone else first runs `fw.py snapshot PROJECT_DIR "$HERMES_KANBAN_WORKSPACE" --expect <MANIFEST>` and works only in the printed `src_dir`. `write_file`/`patch` only with absolute paths under `$HERMES_KANBAN_WORKSPACE` (a hook enforces this).
- If snapshot exits 4 or 5, do not work around it: verifier verdict FAIL, reviewer CHANGES_REQUIRED, with finding `F0|BLOCKER|-|.factory/SHA256SUMS|manifest mismatch: expected <X> got <Y>`. Exit 2 or 3 means your own invocation is wrong: fix it and rerun.
- Cycle 2+ readers: `fw.py delta <BASELINE_TGZ> <src_dir> "$HERMES_KANBAN_WORKSPACE/delta.diff"`; BASELINE_TGZ `none` means review the whole manifest. Review the delta first, then its interactions with unchanged code. Report lockfile changes as before/after `npm ls --depth=0`, not as a raw diff.
- Probes: ignore the runtime "Scratch directory" hint for files you create: write_file/patch go only under `$HERMES_KANBAN_WORKSPACE` (writers: `PROJECT_DIR/.factory/tmp/`); TMPDIR for tool-internal temp files is fine. Save probe scripts, reports, screenshots and delta.diff directly under `$HERMES_KANBAN_WORKSPACE`, never inside `src-<sha12>/` or `base-<sha12>/`. A script there cannot import the copy's packages with bare imports; resolve them from the copy (`createRequire("<src_dir>/package.json")`, or an absolute path into `<src_dir>/node_modules`). Start servers you need (`npm run preview`, a static server) with the terminal tool's `background=true`, from `src_dir`, and stop them before completing.
- Readers finish with `fw.py clean "$HERMES_KANBAN_WORKSPACE"` (removes those copies, keeps tarballs and reports), then complete. A declared artifact that no longer exists keeps the card in flight, and so does one over 25 MB: attach a snapshot tarball only if `fw.py snapshot` printed `"attachable": true`.

## Git and publishing
Never run a Git write (init, add, commit, push, branch/tag/stash/checkout/reset and similar) or any gh command other than a read-only `gh api` GET; approvals.deny blocks them, and a BLOCKED result is final: never rephrase, quote, script, alias or background it. Read-only git with a plain, unquoted verb (status, log, diff, show, rev-parse) is allowed.

## Handoff (kanban_complete)
- `summary` first line: `VERDICT=<v> STAGE=<stage> CYCLE=<n> MANIFEST=<sha12|none>`, then 1-3 sentences. `<v>`: PLAN and writers `DONE` or `BLOCKED` (with `blocked_reason` in metadata); verifier `PASS` or `FAIL`; reviewers `NO_BLOCKING_FINDINGS` or `CHANGES_REQUIRED`.
- `metadata` (JSON under 3,500 chars):
  - `contract`: exactly `"factory-worker/v2"` (proof to the gate that this contract was loaded)
  - `stage`, `cycle`, `verdict`, `root`, `manifest_sha12`, `baseline_sha12`
  - `ac_ids` (PLAN, writers); `ac_results` (verifier): `{"AC1": "pass"}`, `"fail"`, or `"unverified:<cause>"` with cause `code` (the product lacks or breaks it), `harness` (the project lacks a test or probe hook a developer can add) or `environment` (needs a device, account, manual play or anything this headless machine lacks)
  - `findings`: one string per BLOCKER, HIGH and MEDIUM finding, `"F<n>|<SEV>|<AC id or ->|<file:line>|<problem>"`, BLOCKER and HIGH first, at most 15; `findings_truncated`: how many more are only in report.md; `findings_low`, `findings_nit`: counts
  - `checks_run`, `checks_failed` (counts), `failed_checks` (short command strings)
  - writers: `changed_files`; FIX: `findings_fixed`, `rejected_findings` (with the evidence file:line)
  - `blocked_tools`: `[{"cmd": "...", "block": "<first 200 chars>", "needed_for": "<AC id or security>", "attempts": n}]`
  - `residual_risk`, `followups`: short strings
- Readers write the full report (every finding with impact, scenario and resolution; each check with cmd, exit, summary) to `$HERMES_KANBAN_WORKSPACE/report.md` and pass it, plus every cited probe script, screenshot and delta.diff, in `kanban_complete(artifacts=[absolute paths])`. Scratch is deleted after completion; only declared artifacts survive, and their stored paths are written back to `metadata.artifacts`.
- Writers: dir workspaces are never persisted as artifacts, so everything the gate needs goes in metadata.
- Do not manufacture findings. Never claim a check ran unless it ran in this run. Never put secrets, tokens or raw PII in summary or metadata.

## Scanner and approval blocks (headless)
Package commands:
- Pin exact versions in every install: `npm install -D vite@6.4.3 vitest@4.1.11`. Never `@latest`, `^`, `~`, ranges or dist-tags: Tirith cannot verify them, and in headless mode that always blocks.
- Never append `2>&1`, `>`, `| tee`, `| tail` or `| head` to `npm install`, `npm ci`, `npm add` or `npx`; Tirith reads those tokens as package names. Run the plain command (the terminal tool already returns output). Dropping only those tokens is allowed: the plain command is still scanned.
- Read-only probes: `npm ls --depth=0`, `npm view 'vite' version` (quote the name), `ls node_modules/.bin`. Avoid `npx <pkg> --version` and an unquoted `vite` followed by a space (`npm view vite ...`, `npx vite build`), which trips the dev-server guard. Build and test with `npm run build` and `npm test`.
Vulnerable pinned version (Tirith OSV finding naming a GHSA/CVE for a plan-pinned package): look up the advisory's fixed version (`curl -s https://api.osv.dev/v1/vulns/<id>`), pick the lowest fixed exact version of the SAME package that `npm view '<pkg>' versions` lists, install that exact version (still scanned), adjust config/tests for its API if needed, and record `{"pkg", "planned", "installed", "advisory"}` in metadata `dependency_changes` and residual_risk. This is a plan correction, not a block. If no fixed version exists or the fixed version is also flagged, stop as below.
Local servers: always address them as `http://localhost:<port>/` with the scheme (never a bare `127.0.0.1:<port>` or schemeless host:port, which Tirith flags as raw-IP/schemeless URLs); start previews with `--host localhost`.
Transient Tirith blocks:
- If a block names a real package and says "lookup deadline exhausted" or "upstream returned an error status", run `sleep 60` in the foreground (timeout 90), then retry the identical exact-pinned command once.
- If the identical retry is blocked again with the same lookup-deadline/upstream-error reason and the command installs more than one package, split it: install each package in its own exact-pinned command (same packages, same versions, same -D flag), each still fully scanned. Each single-package command gets the same once-after-`sleep 60` retry. This is the only allowed split.
- If a single-package command is still blocked after its retry, stop. Never substitute another package, an older or known-vulnerable version, or a git/tarball/URL source; never move the install into a package.json edit plus bare `npm install`/`npm ci`; never split an install except as described above; never disable Tirith (TIRITH_* env, --offline, config edits). Record it in `blocked_tools`, say in the summary which AC is unmet, and complete.
Headless pattern denials:
- `python3 -c`, `node -e`, `perl -e`, `ruby -e`, `bash -c`, `sh -c`, `-lc` and interpreter heredocs are denied in headless runs. Write the script with write_file (readers: into `$HERMES_KANBAN_WORKSPACE`; writers: into `PROJECT_DIR/.factory/tmp/`) and run it by path, e.g. `node "$HERMES_KANBAN_WORKSPACE/probe.mjs"`. For inspection use read_file and search_files. This exception covers only inline interpreter code: any other denied command (recursive or forced deletes, chmod -R, curl|sh, kill, git/gh writes) must never be moved into a script.
Hard rules:
- approvals.deny or hardline blocks, and Tirith findings other than incomplete verification (malicious, typosquat, OSV-vulnerable, pipe-to-shell) are final: never rephrase, retry or route around them. Record the block in `blocked_tools` and complete; do not `kanban_block` for it. A write-guard block on a wrong path is a path correction, not a tool block: rewrite the file at the allowed path and do not record it in blocked_tools (record only blocks that leave a check unrun).
